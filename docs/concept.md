# 人生のスキルツリー — 構想・初期開発ブリーフ

作成日: 2026-10-23  
状態: 初期構想。確定した方向性と実装上の提案を区別して記す。  
想定配置: `docs/concept.md`  
対象読者: 本リポジトリを実装するClaude、および開発者。

## 1. 作りたいもの

人生のさまざまな分野について、「何を学べるか」「その先で何ができるようになるか」を、入れ子になったスキルのグラフとして探索できるアプリケーション。

ユーザーが分野別のツリーを作り、交換し、取り込んだものを自由に編集・部分利用・組み合わせできる。個人の実績や学習記録を重ね、自己研鑽の可視化にも使う。

ただし、進捗を埋めることだけが価値ではない。「これを進めると、こんな強そうなスキルに届くのか」と想像が膨らむことが核である。自分の記録が一切なくても、眺め、移動し、内部を開くだけで面白いものを目指す。

初期版では、その探索体験を実際に動く形で成立させる。一般的な管理画面にグラフを添えたものではなく、グラフの空間そのものを主役にする。

## 2. 背景とこれまでの障壁

以前からあった構想だが、主に二つの難しさにより着手できていなかった。

1. 分野の体系、前提関係、実績条件までツリーとして作る作業が大きい。
2. 入れ子や別の枝へのリンクを含む複雑なグラフを、見やすく、魅力的に描画するのが難しい。

Cytoscape.jsとELK.jsを知ったことが再検討のきっかけとなった。今回の開発では、これらがどこを担えるかを検証する。名前だけ採用し、実際は別の簡易描画で済ませて技術検証が完了したことにしない。

会話中に作られた障害影響シミュレーターは、本プロジェクトの仕様・成果物・実装基盤として扱わない。本書を起点にリポジトリで開発する。

## 3. 確定している方向性

- 分野の内部にさらにグラフがある、入れ子の構造を扱う。
- 例: 人生全体 → 数学 → 解析学 → 極限・微分・積分。
- 包含関係と学習の前提関係は別の構造である。
- 別の枝へのリンク、とりわけ入れ子の境界をまたぐリンクを扱う。
- 他人のツリーを取り込み、自分向けに修正し、一部だけ取り出し、他と組み合わせられることが必要。
- 達成条件に一律の正解を置かない。分野や作り手によって自由に定義できる。
- 「100時間勉強した」「特定のテストで100点を取った」などの実績を想定する。
- スキルツリーと実績ツリーを同一概念に押し込めない。関係はあるが、別物として検討する。
- ゲームらしいリッチな動きは、付加的な装飾ではなく、探索体験の重要な要件。
- 自由なx・y・z座標をユーザーに設計させない。制作と交換を難しくするため。
- グラフ構造から配置を生成し、その上に3D風の表現と視点移動を重ねる。

## 4. 目指す探索体験

### 4.1 全体像

奥行きを感じる空間にノードと接続が配置される。ノードには控えめな浮遊、発光、呼吸するような変化があり、静止して見ていても生命感がある。文字が揺れて読めない、線の意味が追えないほど動かさない。

未達の遠いノードも、その存在や魅力を知れる。ゲーム風だからといって、未達の内容をすべて隠さない。

### 4.2 ノードを選ぶ

クリックしたノードが画面中央に来るように視点が移動する。一定速度ではなく、exponentialなトランジションを求める。初期の解釈は「出だしが速く、目的地に近づくほど滑らかに減速するease-out系」。具体的な曲線は試作で調整する。

視点移動と連動して説明文が現れる。説明パネルを出した結果、選択ノードが隠れる配置にしない。説明には、そのスキルの概要だけでなく「何ができるようになるか」「先に何がつながるか」を書ける。

### 4.3 入れ子を開く

対象ノードへ急速に接近する。その接近に合わせて、内部のグラフがふわっと浮き出てくる。

単なる画面遷移、瞬間的な図の差し替え、親の枠を広げるだけの表現では足りない。「このノードの内部へ入った」と感じられる連続性を持たせる。

### 4.4 戻る

戻る操作は初期版から必要。前の階層で選んでいたノード、視点、拡大率を復元し、探索の文脈を失わせない。動きは入る操作との関係が分かるものにする。パンくずで現在地を確認できる。

### 4.5 別の枝へ移動する

階層をまたぐリンクは、選択したノードに関係するものを追えるようにする。全階層の全リンクを常時描画する必要はない。

表示していない枝への接続を、存在しないことにしてはいけない。「別の枝に関連先がある」と分かり、その名前と所属を確認して移動できること。移動後も戻れること。

### 4.6 参考作品との関係

発端の参考はFF13のクリスタリウム。ただし動画を見直した結果、実物の動きは記憶より少なく、求める体験と異なると分かった。忠実な再現を要求していない。上記の言語化された動作を優先し、固有の画面・素材を複製しない。

## 5. スキルと実績

### 5.1 意味を分ける

| 概念 | 役割 | 例 |
| --- | --- | --- |
| 分野・グループ | 探索のまとまり、内部グラフへの入口 | 数学、解析学 |
| スキル | 知識・能力・できること | 微分を扱う、最適化を理解する |
| 実績定義 | 達成の基準や挑戦 | 100時間学習、テスト100点 |
| 個人の記録 | その人が残した事実や申告 | 学習120分、点数100、達成日 |

この区分は実装の初期提案であり、すべてを同じノード型で表現するか、実績を別データとして持つかは未決定。

「100時間勉強した」は「そのスキルを習得した」と同義ではない。実績から習得を自動断定しない。一つのスキルに複数の実績、一つの実績に複数のスキルが関係し得る。

### 5.2 条件の自由度

初期のデータ表現は、説明文による自由な条件を失わず保持できるようにする。将来的には累計時間、回数、点数、単発達成、複数条件の組み合わせ等を検討する。

最初から万能な条件式エンジンや外部サービスによる自動認定を作る必要はない。交換されたデータに任意のJavaScriptを埋め込んで実行する設計にはしない。

## 6. 構造と配置を分離する

### 6.1 正本となるもの

ツリーの正本は、ノード、包含関係、関係の種類、説明、実績定義などの意味情報である。画面サイズ、カメラ位置、描画ライブラリの内部IDを前提にしない。

包含関係は循環のない階層として扱う案を基本とする。一つのノードを複数の親へ実体として所属させるかは未決定。初期版では「単一の親＋別の枝からの参照」で成立するかを検証する。

前提関係と関連リンクは、包含とは独立したエッジとして表す。前提関係は循環を検出し、関連リンクの循環と区別する。単なる関連をすべて解放条件にしない。

### 6.2 表示用に生成するもの

- 現在の階層と展開状態に応じた表示グラフ。
- 自動レイアウトによる平面上の位置。
- 表示のための奥行き、傾き、スケール。
- 閉じた枝のリンクを示す代理表示。
- カメラの目標位置、説明パネルとの調整。

ユーザーが自由な3D座標を入力・調整しなければ成立しない設計は採用しない。奥行きは読みやすさを保つ規則から生成する。視覚効果で動かしても、レイアウトの基準位置は安定させる。

同じ構造なら毎回概ね同じ配置になることを目指す。選択だけで全体を再配置しない。レイアウトのキャッシュは交換用データの必須要素にしない。

## 7. 技術構成の検証方針

### 7.1 役割の候補

| 層 | 候補・役割 |
| --- | --- |
| 意味モデル | UIから独立したTypeScriptのデータと操作 |
| 表示グラフ生成 | 階層、選択、可視範囲から表示対象を生成 |
| 自動配置 | ELK.jsを第一候補として検証 |
| グラフ表示・操作 | Cytoscape.jsを検証。ただし必要なカメラ演出への適性は未確定 |
| 3D風の描画 | 必要ならThree.js等のWebGL描画を候補に比較 |
| 説明・編集UI | 通常のHTML UI。グラフと同じ意味モデルを参照 |

これは採用済みの依存パッケージ一覧ではない。Claudeは実装時点の公式ドキュメント、対応バージョン、ライセンス、実機の挙動を確認すること。

### 7.2 調査で分かっていることと、分かっていないこと

Cytoscape.jsはcompound nodesによる入れ子をサポートする。ELKには複数階層を同じレイアウトで扱う`hierarchyHandling`がある。ただし、それだけで希望する演出、折り畳み、階層をまたぐリンクが完成するわけではない。

Cytoscape.jsで得られるノード位置と、ELKが生成するエッジ経路が、同じように描画されるとは仮定しない。座標系、親子のオフセット、親の寸法、折れ線の反映方法を実測する。

ELKを3Dレイアウトエンジンとして扱わない。構造の読みやすい配置を計算し、その後に表示上の奥行きを付ける構成を検証する。

### 7.3 最初の技術スパイク

同じ小規模なデータで、次を短く比較する。

1. Cytoscape.js＋ELK.jsで、入れ子、階層越えリンク、視点移動の成立範囲を確認する。
2. 欲しい表現が難しい場合、ELK.jsの配置を独立した描画層へ渡す案を試す。必要ならWebGLを使う。
3. 結果を短い技術判断記録に残し、最終構成を選ぶ。

二つの本格的なアプリを並行開発しない。Cytoscape.jsに無理やり透視投影を載せることも、検証せず捨てることも避ける。最終的に採用しない場合も、理由と実際に試した範囲を残す。

最終的な判断軸は、探索の気持ちよさ、リンクの可読性、編集と交換のしやすさ、保守性である。

## 8. 最初に完成させる縦切りの試作

以下は、構想を具体的に検証するための初期実装提案。

### 8.1 サンプルデータ

- 二〜三階層、全体で20〜40ノード程度。
- 数学を中心に、初等数学、解析学、線形代数、その内部のスキルを用意。
- 機械学習等の別の枝も少数用意し、階層をまたぐ接続を必ず含める。
- 学問的に厳密なカリキュラムと主張しない。探索体験を確かめる例として明示する。
- 各ノードに「何ができるようになるか」を書く。名前だけの大量ノードで埋めない。
- 記録がなくても遠くの到達点を知れる。

### 8.2 必須の操作

- ノードの選択、中央への滑らかな視点移動、説明表示。
- 入れ子への接近、内部グラフの出現。
- 元の階層・視点への復帰、現在地の表示。
- 別の枝への接続の発見、移動、戻る操作。
- 控えめな常時アニメーション。
- 日本語のラベルと説明の読みやすい表示。
- クリックの連打や途中の別ノード選択で破綻しない遷移。

### 8.3 作成・交換の最小経路

最初からコミュニティやサーバーを作る必要はないが、固定データ専用の作品にしない。

- バージョン付きJSONを読み込み、書き出せる。
- ノードの追加、説明編集、親の指定、関係の追加・削除を、座標編集なしで行える小さな編集UI。
- 他のツリーを取り込み、一部の枝をコピーして組み合わせる最小経路。
- コピー時にID衝突を解決し、取り込み元情報を保持する。
- 部分書き出しでは、対象外へのリンクをどう扱ったかを示す。参照切れを黙って消さない。
- ローカル保存と、未保存変更の扱い。

探索演出の成立確認を先に行い、その後にこの経路をつなぐ。初回試作の完了状況は、探索・編集・交換を分けて報告する。

### 8.4 今回は完成を求めないもの

- ログイン、クラウド同期、公開マーケット、ランキング、他者評価。
- 網羅的な人生全体のカリキュラム。
- 完全な実績条件エンジン、外部サービス連携。
- 取り込み元の更新を自動マージする仕組み。
- 自由な3Dモデリング・座標編集機能。

将来の方向性を消すための除外ではなく、まず魅力と技術的成立を確かめるための順序である。

## 9. 作る負担を下げる設計

描画が自動になっても、内容を考える負担は残る。以下を実装・設計の評価軸にする。

- 到達点だけ先に置き、途中を後から詳しくできる。
- 未完成の枝を未完成のまま保存・交換できる。
- グループの内部が空でも壊れない。
- 他人の枝を取り込み、条件や説明を自分向けに変えられる。
- グラフ上で親・前提・関連を追加でき、座標や描画パラメータを知らなくてよい。
- 意味の違う関係を一本の無名の線へ押し込めない。

AIによる草案生成は将来の選択肢だが、今回の必須機能にはしない。人が少しずつ作れることを先に成立させる。

## 10. データ交換の設計メモ

推奨するトップレベル情報は`schemaVersion`、ツリーID、タイトル、説明、ノード、関係、作成者・出典等。正式なスキーマは実装時に定義する。

個人の学習記録は共有用の定義と分離する。書き出しで他人に個人の進捗まで渡すことを既定動作にしない。

取り込み後の編集は自由とし、元のツリーを破壊しないコピーを基本案とする。出典と元IDを残す。元の更新との自動同期や、異なるツリーの「同じSQLスキル」を自動同一視する機能は後回しにする。

入力の検証対象には、ID重複、包含の循環、存在しない参照、関係種別、過大なデータを含める。説明文はテキストまたは安全に表示できる形式で扱う。

## 11. 動きと品質の受け入れ条件

- ノードの選択で、対象と視点の関係が追える。唐突な瞬間移動にならない。
- 内部へ入るとき、接近と子グラフの出現が一連の動作として感じられる。
- 戻ると、元の位置関係を思い出せる。
- 別の枝へ移動しても、現在地と帰り道が分かる。
- 閉じた階層へのリンクの存在と相手を確認できる。
- 連打、遷移中の戻る、データ切り替えでカメラや説明が別のノードを指さない。
- 表示サイズ変更に対応し、説明文と選択対象が両立する。
- アニメーション低減設定では、揺れ・発光・大きな接近演出を抑えても操作できる。
- アニメーションは描画だけに作用し、ノードの意味・達成条件・保存データを変更しない。
- 長いラベル、空のグループ、循環する関連、複数階層の接続で破綻しない。

初期の調整値の候補は、選択移動350〜650ms、内部への遷移650〜1000ms。これはユーザー合意済みの値ではなく、触って比較する出発点。速度、減速、子グラフの出現タイミング、奥行き、浮遊量を一か所で調整できるようにする。

性能は対象端末とノード数を記録して測る。最初はデスクトップで20〜40ノードを滑らかに操作できること。大規模対応を未検証のまま保証しない。ELKの計算が重ければWorker化やキャッシュを検討し、毎フレーム再計算しない。

## 12. Claudeへの実装依頼

本書を読んだ上で、動くリポジトリを作ってください。細部を質問で埋め尽くさず、可逆的な実装判断は仮定を明記して進めてください。体験の核を削る必要がある場合は、変更理由を示してください。

特に挑戦してほしいのは、次の点です。

> 見た瞬間に図として理解でき、触るとゲームの成長空間を探索する気分になること。ノードへ吸い込まれ、その中に次の世界が現れる動きを、実際に触って気持ちよい水準まで作ること。

### 実装順序

1. 意味モデルと小さなサンプルを用意する。
2. Cytoscape.jsとELK.jsの実動作を検証し、描画構成を決める。
3. 選択・接近・内部出現・復帰・階層越え移動を一連の体験として完成させる。
4. 速度や奥行きを調整し、文字とリンクの読みやすさを確認する。
5. 最小の編集・保存・入出力・部分取り込みをつなぐ。
6. 検証結果と未実装部分を文書化する。

### 実装上の注意

- UIフレームワーク等はリポジトリの事情に合わせて選ぶ。既存構成がなければ、Vite＋TypeScript等の小さな開発構成を候補とする。
- 意味モデル、レイアウト、描画、遷移状態、UI、永続化を分離する。描画ライブラリのオブジェクトを保存形式の正本にしない。
- 遷移の中断・再選択・戻る操作を設計し、アニメーションを場当たり的に積み重ねない。
- 本物のカメラや視点変換でなくても目指す体験を実現できればよいが、スクリーンショットだけの演出や操作不能なモックで完了としない。
- 必要なライブラリが取得できない場合は、その具体的なブロッカーを報告する。別方式の代用品を使って採用技術の検証が済んだと報告しない。
- 仮の未実装ボタン、動かない編集項目を完成品のように並べない。
- 技術選定の合理性と同じくらい、動きの仕上げに時間を使う。

### 必要な検証

データ検証、部分取り込み時のID・参照処理、包含と表示グラフ生成には意味のあるテストを置く。探索・遷移・視覚表現は実ブラウザで確認する。少なくとも、ノード選択、二階層の出入り、階層越え移動、遷移中の再選択、JSON往復を確認する。

成果報告にはスクリーンショットに加え、可能なら短い操作動画を含める。動きが主題なので、静止画だけでは検証完了としない。自動検証が難しい主観的な質は、人が見て調整すべき項目として残す。

### リポジトリに残す成果物

- ローカルで起動できるアプリと、再現可能な依存定義。
- 起動方法と操作方法を記したREADME。
- 本構想書。
- 採用構成とCytoscape.js／ELK.jsの検証結果を記した短い技術判断記録。
- サンプルのツリー定義と交換用スキーマ。
- 受け入れ条件の確認結果、制約、未実装部分。

## 13. 未決定事項

次は未決定であり、本書の確定要件として勝手に固定しない。

- スキルと実績を切り替え表示するか、関連する別画面とするか。
- 分野ノード自体の達成・習得を定義するか、子の進捗をどう集約するか。
- 前提スキルを強制的なロックとするか、学習上の案内とするか。
- 同じスキルを複数ツリー間で同一実体として共有する方法。
- 作成者の更新の取り込み、差分と競合の扱い。
- 公開・共有の運用、ライセンス、検索・発見の仕組み。

探索試作では、未達ノードの説明も閲覧可能とし、強制ロックなしを仮置きにする。後で変更できる構造にする。
